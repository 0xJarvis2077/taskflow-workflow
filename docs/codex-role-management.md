# Role-local Codex management

Python selects the confirmed provider, model, reasoning effort, credential environment variable name, CLI artifact and role-local model catalog. Codex owns its agent loop, native tools, execution and context. No new agent protocol or execution engine is introduced here.

Current role tasks use the explicit [material revision](material-revisions.md), [quality](quality-tasks.md) and [formal solving/review](formal-review-tasks.md) entries. Solver tasks run through native Codex with a fresh role session; facts and score continue the same reviewer session after sealing. The adapter and initial-slice details below describe retained supporting components, not a replacement for those task contracts.

`native_provider` is optional. Without it the existing native runner remains unchanged. When supplied it references a `codex_role_provider_v1` JSON document with exact `provider`, official `base_url`, `wire_api=responses`, `credential_env`, `model`, `reasoning_effort`, `cli`, `catalog`, `codex_home` and `documentation` fields. Every file reference has absolute path, SHA256, size and location. Batch freezing captures those original bytes; preparation locks the actual CLI and referenced dependencies again. Credential values are selected at launch from the existing trusted environment, never written to the provider document or model-visible files. The standalone worker passes only that selected provider variable to Codex and gives model shell tools no inherited environment.

The role-local catalog retains the chosen model and explicit supported effort, and selects Codex native direct tools. It changes neither global configuration nor the chosen model. Local tool networking and web search are disabled. Model service access remains with Codex. New native and public-rebuild preparations leave Codex request and stream retry options at the selected CLI configuration defaults. Formal adapter rendering preserves legacy bytes by default; a new adapter may explicitly select `transport_retry_mode="codex_default_v1"` and bind its new sources and authorization. Effective retry counts, delay and independent connection behavior are not observed by this setting. `automatic_retry: false` in new metadata describes business-work redispatch only (`automatic_retry_scope: business_work_redispatch`); the separate transport field records the Codex configuration selection. This transport behavior does not authorize a new business attempt or resume a terminal session; existing frozen requests retain their original options and actual history.

The first slice enables the existing logical `content_inspector` slot with first-class native role `content-inspector`. It accepts only public, operation, skill and knowledge inputs. Unlike the teacher-informed quality role it cannot receive references, answers or scoring. The existing enqueue path adds exactly the managed candidate public originals. Preparation and enqueue do not start a model. Existing task pause remains until the exact execution dependency and source candidate are reviewed within the applicable engineering and runtime conditions, followed by normal native preflight and one whitelisted worker call.

The local CLI policy derivation is an explicit external artifact under separate review; this source does not declare it an official release or authorize production installation. Offline fixture results are synthetic and prove no business outcome. A failed official-source build remains failed. The slice does not accept unresolved direct-API scoring candidates, repair or replace their history, or resume their paused dispatch.

Verification uses `python3 -m unittest tests.test_execution_codex_provider tests.test_execution_runner tests.test_execution_batch tests.test_execution_batch_binding tests.test_execution_batch_sources tests.test_execution_batch_dispatch -q` with provider credentials removed. This is offline management and compatibility validation; actual business quality and later solver/facts/score stages require their own normal evidence.

## Custom-provider metadata

Native provider preparation validates the explicitly referenced role catalog rather than requiring custom models to appear in the bundled OpenAI catalog. It still retains the original CLI version and bundled-catalog command evidence. These are different sources: CLI commands prove only their ordinary successful completion; role metadata declares the selected model and effort. Neither source proves outbound requests, account access or served identity. The manifest records the role catalog and leaves resolved/served identity unknown.

The DeepSeek Responses API documents `medium` as an accepted compatibility alias mapped by the service to `high`. The requested value stays `medium`; a role-local catalog may declare that accepted alias with its documentation source. Each role retains its explicitly selected effort. No caller silently changes the requested effort. Official sources: https://api-docs.deepseek.com/api/create-response/ and https://api-docs.deepseek.com/quick_start/agent_integrations/codex/ . Codex model catalog configuration: https://learn.chatgpt.com/docs/config-file/config-reference .

Engineering self-review belongs to the implementing owner; no permanent independent engineering chat is required. This does not replace independent business quality, solver or facts/score roles. Prior failures, unresolved runtime isolation, platform interruptions and unknown server execution remain recorded. Ordinary configuration tests do not close those gaps. An ownership change does not activate prepared work, authorize restricted checks or establish acceptance. Use an applicable reviewed official execution configuration only when all actual runtime requirements are established; otherwise retain the concrete missing condition without requesting the same user authorization again.

## Optional provider propagation

The batch compiler, initial author, author successor roles and flow settings copy the optional native provider reference from the confirmed selection. An absent choice clears an obsolete template value. The facts/score preparation keeps the selected provider home declaration when constructing its role-local filesystem configuration. This carries configuration only; it does not establish OS enforcement or provider access.

The existing public-rebuild adapter preserves the provider reference, materializes the selected Codex options into its locked plan and captures the provider/catalog/documentation dependencies. Its copied launcher uses the same standalone process-environment helper as native roles. The retained formal adapter renderer versions its approved source with the explicit provider and effort; it keeps the adapter capture/run contract, records provider source dependencies and uses the same environment-selection helper. Adapter preparation rejects a mismatched or unbound provider reference. Current native solver tasks follow the separate formal task contract. Facts and score require the same provider reference as well as their same-context checks. These are configuration and launch-management capabilities; OS enforcement and business readiness remain separate.

## Real connectivity verification

`python3 -m tools.codex_connectivity --profile /absolute/provider.json --output /absolute/new-attempt` performs only local configuration preflight. Add `--execute` only for an authorized actual connection request. The selected profile uses the same explicit provider/model/effort/catalog/credential-variable references. Python launches official Codex in a new empty home/work directory. The connectivity catalog and settings disable command execution, patching, images, Code Mode, apps, plugins and other unused capabilities. The request contains only a fixed acknowledgement prompt. It sends no business task, Skill, answer or scoring materials.

Each provider uses one new output directory and an append-only logical claim. An existing directory is never reused, including after failure or timeout; the command does not automatically reissue a request. The retained request, original JSON stdout, stderr and result include the configured endpoint/model/effort, Codex SID and exposed usage. Credentials are selected only in process memory and redacted from captured stdout/stderr if present. A Codex SID is not a provider response ID; missing served-model/response identity remains unknown. Completed assistant acknowledgement plus turn completion and exit zero establish this connection result. Startup feature warnings stay in the evidence and are distinguished from errors and tool activity.

Tool-free connectivity success does not qualify arbitrary model tools, external credential isolation or a business task. Existing unresolved runtime requirements and platform restrictions remain recorded. A successful connection does not authorize restricted checks, activate a different CLI or reset existing work. Business execution stays with its assigned owner and existing gates.

## Read-only content inspection without model tools

A native `content-inspector` runner may explicitly select `text_only_delivery={"schema": <absolute SHA/size reference>, "output": "deliverables/inspection.json"}` with exactly that one declared output and no output trees. The response schema must declare an object. The normal managed policy/provider/model/effort and candidate binding still apply. Each role needs its own empty Codex home; prior role homes are rejected at launch. This capability is deliberately unavailable to formal solvers and other execution roles.

Preparation preserves every typed UTF-8 input in the existing frozen input tree, renders complete line-numbered original contents into the request, and locks a complete input membership/hash/line-count index. There is no truncation or omitted-file fallback. Non-text inputs cannot be silently converted or dropped. The caller must supply the entire public/method selection authorized for this role through the existing typed inputs, not an alternative summary. No additional Knowledge/Skill discovery is enabled.

The same official Codex model/provider configuration is used with command, patch, image, Code Mode, apps, plugins and other unused tool capabilities disabled. Codex's `--output-schema` and `-o` capture the original structured assistant response; the management layer collects it through the normal worker, retains stdout/SID/request/input originals and checks that the captured object equals the final response. Unexpected tool activity or errors prevent technical acceptance. Business findings and field validity remain the role owner's responsibility. The caller's normal `enqueue_spec(..., probe_native=True)` selects the bound text-only configuration-readiness check for this capability; it does not run or claim an execution-tool permission probe. Existing tool-enabled roles keep their original requirements.

Existing prepared work is never changed by opting into this mode. A business owner must explicitly bind a legitimate unique technical continuation/replacement and preserve the old work, pause, inputs and purpose linkage. This manager capability does not reset/requeue it or grant a new business purpose. Static-content equivalence belongs to its controller; solver execution and metering duties are unchanged.

## Explicit ChatGPT consumer startup environment

`python3 -m tools.codex_managed_start --cwd /absolute/repository --receipt /absolute/new-start.json -- /absolute/python -m taskflow execution <original arguments>` shows a names-only startup declaration and starts nothing. With an independently authorized and ready original consumer, adding `--execute` launches precisely that existing Python entry with the explicit ChatGPT environment selector. It preserves core login/home/runtime/proxy/certificate configuration names, omits unrelated API-key/token variables, creates a one-time startup intent and records the PID. It never changes a frozen worker/request, model, task or work ID. Each original execution entry keeps its normal locks, holds and business gates.

This changes only what is passed into the new consumer and its inheriting supervisor/Codex descendants. The ordinary positive test uses three neutral Python subprocess layers and inspects their own environment names; it does not inspect any parent/startup information or perform a sandbox check. This does not prove protection from credential-bearing ancestors or other trusted processes, or satisfy unresolved tool-enabled launch conditions. Offline validation does not start a business consumer.
