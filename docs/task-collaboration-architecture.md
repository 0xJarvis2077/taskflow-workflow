# 出题协作架构与批次启动

版本：high-value-task-v1。固定职责、隔离及接续契约；具体题数、题目、模型、聊天名称和 ID 由批次配置。

## 职责与身份

| 逻辑角色 | 工作 | 边界 |
| --- | --- | --- |
| `coordinator` 研发主控 | 目标、真实业务增难、投入选择、派工、版本与证据接收 | 不常规重评，不逐单处理中转技术操作 |
| `author` 研究作者 | 行业研究、完整业务任务、材料、私有参考与正常对照 | 作者推演不是正式压测，不给自己的修订签独立通过 |
| `public_rebuild` 独立公开重建 | 只据当前公开输入完成独立业务工作 | 不加载教师设计、答案或历史分数 |
| `quality` 独立质量 | 整包可解性、公开判断归属、参考与评分核验 | 公开先行责任记录，后对照教师；不同时充当返修者 |
| `repair` 返修 | 据具体问题修改材料、参考与规则 | 保留必要条件、正常分支及旧版原件 |
| `recheck` 独立复检 | 核真实改动与必要关联，验证问题关闭 | 不将局部复检冒称新整包审查 |
| `solver` 正式作答 | 接收同版公开题面及业务附件并交付 | 独立新上下文及实际文件隔离，不接教师目标或答案 |
| `reviewer` 两阶段评阅 | 先封存全卷事实，再按同版冻结参考评分 | 事实与评分使用同一模型及同一实际 SID |
| `content_inspector` 内容检查 | 审查公开材料是否提供过多分析结果、提前完成拟测判断；公开预解题与相关制作声明清理，跟进实际修改 | 按[加工边界](../knowledge/methods/design-review.md#公开材料的加工边界)核原句及跨文件答案链；不评分、不作例行放行、不查日常 PID 或负责调度 |
| `engineer` 执行工程 | 确切工程修复、补丁验收、恢复及接续验证 | 有任务时介入，有限验收后待命；不等题目达标才收口 |
| `health_auditor` 健康巡检 | 核跨角色真实推进，有据纠偏 | 不重复评分、创建新调度层或无变化反复催促 |

这些是可分别配置模型的逻辑槽位，不要求每题常驻十一套聊天。只有实际需要时才派相应独立上下文；正式作答、独立质量／复检与两阶段评阅的边界不能因节省聊天而合并。使用同一型号不等于使用同一上下文。Python 消费者负责结构检查、状态、互斥、依赖、普通后继派发和回执，没有模型，也不代做业务判断或替用户选择模型。

正常链为：作者完整设计／材料与私有参考 → 独立公开重建 → 独立整包质量 → 必要返修 → 独立复检 → 接收；有明确业务用途和既有授权时才接正式作答 → 独立全卷事实封存 → 原评阅 SID 参考评分 → 主控确定下一研发投入。六题或其他批次数量逐题并行，不等整批一起交接。技术问题只阻塞受影响部分，沿既有 Python 入口恢复；主控仅处理实质业务取舍和授权缺口。内容检查将具体公开预解题问题交现有作者／返修消费，不增加一层终审。

## 每批必须先确认模型

1. 从[空模板](../knowledge/templates/task-batch-plan.template.json)建立该批私有启动记录，填批次 ID、行业／题目范围、逻辑角色及载体。所有新批次模型初始为空，历史 factory、policy、模型目录和 CLI 默认不提供人的选择。
2. 汇总所有启用角色的未定模型，一次向用户问清。用户可以分别指定，也可以明确“作答用 X，其余用 Y”；只对其明确覆盖的角色展开，缺项继续保持未定。不能把建议、预选项、沉默或等待超时写成人的确认。
3. 保存用户直接选择的原话／消息定位和适用范围，展开后的逐角色模型须与之对应；助手填全表本身不证明用户选过。确认内容与模型映射分别绑定字节，映射或范围变化后不得沿用旧确认。
4. 先核所选 CLI／既有服务确实支持所选模型与必要能力，再从本批确认生成新版本策略／工厂。目录不可用、不支持、名称歧义或服务需改变时说明实际缺口并问受影响项，不静默换型号或新服务。推理参数按用户明确要求和该模型支持范围设置，不能把旧 xhigh 或 medium 无条件套给所有模型。
5. 准备和启动核角色、本批确认、实际模型与冻结输入一致。用户未选择或证据未覆盖时不给真实调用兜底默认；缺项以 `awaiting_user_models` 交还用户。不因这些准备工作授权新增付费服务、平台提交或扩大文件权限。

建议的一次询问可以写成：“本批请确认研发主控、作者、公开重建、质量、返修、复检、作答、评阅、内容检查、工程和健康巡检的模型。可以逐项填写，也可以明确‘作答用 X，其余全部用 Y’；尚不启用的角色可暂不配置。”不预填上一批次的型号，不暗示必须选某一强弱模型。

同一已确认批次内，正常迭代、新版本、新独立 CLI 和按原身份恢复不重复问；新增启用角色、换模型、换服务或超出选择范围时，只补问受影响项。新批次重新确认，除非用户曾明确给出覆盖该新批次的持续偏好。不能从一次选择推断永久默认。

主控、工程、内容检查、健康巡检的聊天模型也在表内。执行层尚未替用户创建这些聊天时，由启动者核实际聊天配置；表内填写不能冒称已切换聊天模型。若当前聊天模型无法匹配已选值，说明并按用户选择创建或切换对应载体，不能悄悄用当前会话代替。此规范不自动授权创建新侧栏聊天或定时任务。

## 名称与路由

- 长期协作聊天建议 `出题·<项目或批次>·研发主控`、`出题·<项目或批次>·内容检查`、`出题·<项目或批次>·执行工程`、`出题·<项目或批次>·健康巡检`。需要按题分工时再加题号，不用“接管”“持续实施”等阶段性口号充当永久身份。
- 独立 CLI 的可见工作名建议 `<批次>/<题号>/<版本>/<角色>/<尝试号>`；实际 `work_id` 使用现有执行层允许的字符和长度编码，显示名与结构化字段分别保存，不强行将带斜线标题当作合法 ID。
- 本批绑定保存 `role_key → thread_id + host` 或 `role_key → work_id + attempt_id + SID`，标题仅用于展示与人工核对。重名不能猜路由；改名不换身份，换聊天必须更新绑定。尚未启动的 ID 保持空值，不预造真实 SID。
- 事实封存与参考评分共用 `reviewer` 配置和实际 SID；作者、返修与独立审查的 SID 不得合并。临时实质争议复核是新的独立角色实例，启用模型仍需处于本批用户明确选择范围。

## 记录与实现边界

启动记录、确认原话、模型配置和角色绑定均属内部治理材料，不进入 solver 包。历史记录只证明当时选择，不作为下批默认；保存真正发生的请求、模型请求值、可证客户端配置及服务端未知项，不能将模型表当作服务端身份实证。


显式模型、策略一致性或模型目录支持不能替代用户确认。准备真实角色前，核对本批角色模型及确认来源；执行层尚未覆盖的路径不得借旧默认绕过询问。程序接口与已实现的拦截范围以执行层说明和实际检查结果为准。

新批次使用[有确认门的 `batch-*` 入口](execution-layer.md#新批次模型确认入口)，先核选择和证据，再冻结并编译本批策略／工厂。历史兼容入口不作为新批模型默认或绕过路径；已经授权并锁定的旧批次沿原身份恢复，不迁移或重复询问。
